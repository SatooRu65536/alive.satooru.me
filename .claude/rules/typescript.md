# TypeScript コーディングルール

## 基本方針

- 型は可能な限り明示的に書かず，推論に任せられる箇所は推論に任せること
  - ただし，関数の引数・戻り値には型を明示すること
- `any` は使用しないこと
  - 型が不明な値は `unknown` を使用し，型ガードで絞り込むこと
- 非null演算子（`!`）は使用しないこと
  - null／undefined の可能性がある場合は，型ガードやオプショナルチェイニング（`?.`）で対応すること
- `as` によるキャストは可能な限り避けること
  - やむを得ず使用する場合は，理由をコメントで残すこと
  - `as const` は例外的に許容する
  - `as unknown as T` のようなダブルアサーションは使用しないこと

## 型定義

- オブジェクトの型定義には `interface` を使用し，`type` でなければならない場合のみ `type` を使用すること
  - 例：ユニオン型，タプル型，プリミティブ型のラップなど
- Union型で表現できるものに `enum` は使用しないこと
  - 例：`type AvatarMimeType = 'image/jpeg' | 'image/png';`
- プリミティブ型のラップが必要な場合（ID等）は，ブランド型を検討すること
- リクエストボディ，レスポンスボディ，環境変数などの外部からの値は，型を信用せず実行時にチェックすること

## 命名規則

命名は [naming.md](./naming.md) に準ずる．

## 関数

- 1つの関数は1つの責務のみを持つこと
- 副作用のある関数と純粋な計算を行う関数は分離すること
  - 例）検索条件の組み立て（`searchConditions.ts`）は API へのリクエストを含まない純粋関数として実装する
- 早期リターンを用いてネストを浅く保つこと
- 引数が2つ以上の場合はオブジェクト引数（分割代入）にすること
- 純粋関数を追加した場合，対応するテストを追加すること

## イミュータビリティ

- オブジェクト・配列の直接変更は避け，新しいオブジェクト・配列を生成すること
- 配列操作は `push` / `splice` 等の破壊的メソッドではなく，`map` / `filter` / `reduce` などの非破壊的メソッドを使用すること
- readonly にできるプロパティ・配列（`readonly T[]`, `ReadonlyArray<T>`）には積極的に付与すること

## エラーハンドリング

- 例外は「本当に例外的な状況」でのみ使用し，通常のフロー制御には使用しないこと
- 起こりうる失敗（バリデーションエラー等）は Result 型（例：`{ ok: true, value } | { ok: false, error }`）で表現することを検討すること
- `try/catch` で握りつぶさず，エラーは呼び出し元に伝播させるかログに残すこと

## import / モジュール

- 他のディレクトリ（`components` 等）のモジュールを import する場合は，相対パス（`../`）ではなく `@/` パスエイリアス（`@/components/...` 等，`web/src`・`api/src` を指す）を使用すること
  - 同一ディレクトリ内のモジュールは相対パス（`./`）のままでよい
- import の順序は以下の通りとすること
  1. 標準ライブラリ／外部パッケージ
  2. 内部モジュール（パスエイリアス経由）
  3. 相対パスによる同一機能内のモジュール
- default export は使用せず，named export を使用すること
  - リネーム時の追跡やリファクタリングが容易になるため
  - Storybook の `meta`（`*.stories.tsx`）や設定ファイル（例：`vite.config.ts`）など，ツールが default export を求めるものは例外とする
- export は定義した箇所で行うこと（例：`export function foo() {}`，`export type Foo = ...`）
  - 同じファイルで定義したものを，ファイル末尾でまとめて `export { foo };` のようにエクスポートしないこと
  - feature の `index.tsx` で他のモジュールを `export { Foo } from './components/Foo';` のように再エクスポートするのは構わない
